# Kryonsec — Full Codebase Bug & Logic Audit

**Date:** 2026-09-08
**Scope:** all 36 source files under `src/kryonsec/` (~10,000 lines), installers, `pyproject.toml`, tests
**Method:** every file read line by line across four parallel review passes (Copilot mode, Purple engine, Purple states, Core/CLI/storage). Top findings were independently re-verified against the code, and several were reproduced empirically (wheel build, `execute_tool` call, `ToolAllowlist({})`, round-trip config tests, report render crash).
**Test suite status at audit time:** 288 passed — every bug below is one the tests do not catch (several are actually *locked in* by tests, noted per finding).

**Totals: 2 Critical · 11 High · 16 Medium · 24 Low = 53 findings**

## CRITICAL

### C1. The built wheel contains no Jinja templates — every fresh install crashes on first chat run

- **File:** `pyproject.toml:29-31` (no `[tool.setuptools.package-data]`, no `MANIFEST.in` — confirmed absent)
- **Verified:** built the wheel locally (`pip wheel . --no-deps`) and listed its contents: 39 files, **zero** `.jinja` / `templates/` entries.
- **What's wrong:** plain setuptools only includes data files matched by `MANIFEST.in` or a SCM plugin — neither exists. `install.sh` / `install.ps1` both install via `pip install git+...`, so the shipped package is missing `kryonsec/templates/*.jinja`.
- **When it breaks:** `kryonsec setup` and `--version` work (templates not touched), so the install "succeeds". Then the first `kryonsec` chat run hits `cli.py:136` `env.get_template("system_prompt.jinja")` → `jinja2.TemplateNotFound` → raw traceback, exit 1. Purple mode is equally broken (`hypothesize.py`, `blue_team.py`, `report.py` all load templates from the same missing directory).
- **Fix:**
  ```toml
  [tool.setuptools.package-data]
  kryonsec = ["templates/*.jinja"]
  ```
  plus a smoke test that imports the installed package's template directory.

### C2. Secrets and file contents are sent unredacted to third-party LLMs in the main chat path

- **Files:** `src/kryonsec/copilot/agent.py:209-217`, `src/kryonsec/cli.py` (`/read` handler, `_remember_facts`)
- **Verified:** repo-wide grep — `redact()` / `detect_secrets()` are called from exactly one place: compaction (`copilot/session.py:72-84`). Nothing else in `src/` calls them.
- **What's wrong:** CLAUDE.md rule 4 says secrets are redacted before any LLM call and engagement data / credentials / raw evidence never go to third-party LLMs. In reality:
  - A user who pastes an AWS key into chat sends it to OpenAI verbatim (the `run_agent` loop ships raw messages to `cfg.general_chat_model`).
  - `/read` and the `file_read` tool put **entire file contents** (`.env`, private keys, credentials JSON) into the message list — the normal reason a security person reads a config file.
  - `_remember_facts` additionally ships the first 500 chars of each user turn to `general_search_model`.
  - The "Ollama-only when secrets present" routing exists only in compaction.
- **When it breaks:** any session containing a credential (pasted or read from a file) while `provider == "openai"` — the default configured by the setup wizard.
- **Fix:** run `detect_secrets()` over outgoing messages before each LLM call in `run_agent`/`chat`/`_remember_facts`; when secrets are present, route to `cfg.local_model` (same logic as compaction's `local_only`) or redact/restore around the call.

## HIGH

### H1. The gVisor runtime check can never succeed on a real Docker daemon — Zone B is unreachable everywhere

- **File:** `src/kryonsec/purple/runner.py:100`, same bug in `src/kryonsec/doctor.py:76`
- **Code:**
  ```python
  ["docker", "info", "--format", "{{join .Runtimes \",\"}}"]
  ```
- **What's wrong:** Docker's `.Runtimes` is a Go map; the `join` template function only accepts `[]string`. Docker CLI returns `error calling join: wrong type for value; expected []string; got map[string]...` with a non-zero exit (documented in moby/moby#37584, #37433, docker/cli#1324). `returncode != 0` → `_docker_runtimes()` returns `None` → `sandbox_available()` reports the daemon unreachable **even on a perfectly configured Linux + runsc host**.
- **When it breaks:** every Purple Team engagement on any real Docker install — the loop always HALTs at RECON_ACTIVE with a wrong reason, and `kryonsec doctor` reports gVisor missing when it is registered. Tests mask it: `test_runner.py:20-46` mock `_docker_runtimes` with a comma string.
- **Fix:** `["docker", "info", "--format", "{{range $k, $v := .Runtimes}}{{$k}} {{end}}"]` (or `{{json .Runtimes}}` parsed in Python), plus an integration test against real `docker info`.

### H2. LLM-supplied absolute URL in `target_asset` bypasses target scope — tools attack arbitrary hosts

- **File:** `src/kryonsec/purple/exploit.py:98-100`; same path in `verify.py:122`
- **Verified:** code read confirmed; reproduced by the audit agent — `build_argv("sqlmap", "pakheartjournal.com", "http://evil.example.org/admin?id=1")` produces `["sqlmap", "-u", "http://evil.example.org/admin?id=1", ...]` and **passes `ToolAllowlist.validate` and `check_blocklist`**.
- **Code:**
  ```python
  asset = (target_asset or "").strip()
  if asset.startswith(("http://", "https://")):
      return asset
  ```
- **What's wrong:** `target_asset` is free-form LLM output (`Hypothesis.target_asset`, no host validation). Absolute URLs skip `resolve_host` entirely — the "scope enforced by construction" claim in its docstring only holds for path assets. The `{url}` allowlist pattern (`allowlist.py:26`) checks URL *shape* only, never that the host is the engagement target or subdomain. The hypothesize prompt is fed attacker-influenceable data (Wayback paths, crt.sh names), so prompt injection can steer this. Combined with H5 (no network scope), sqlmap/nikto/ffuf/curl can be aimed at any host.
- **When it breaks:** any engagement where the LLM emits an absolute URL in `target_asset` and the operator approves it (the operator sees one `target:` line among many).
- **Note:** `tests/test_exploit.py:86-87` (`test_compose_url_absolute_asset_kept`) **asserts this bypass as intended behavior** — the test locks in the bug.
- **Fix:** in `compose_url`, reject/rewrite absolute URLs whose host is not the target or a discovered subdomain; update the test to assert rejection of out-of-scope URLs.

### H3. Zone A egress allowlist is bypassed by HTTP redirects — and Wayback is fetched over plain HTTP

- **File:** `src/kryonsec/purple/zonea.py:76-83` (redirect), `zonea.py:171-175` (plain `http://`)
- **Code:**
  ```python
  host = urllib.parse.urlparse(url).hostname or ""
  if host not in ZONE_A_ALLOWED_HOSTS:
      raise ZoneAViolation(...)
  with urllib.request.urlopen(req, timeout=timeout) as r:
  ```
- **What's wrong:** `urlopen` follows 3xx redirects automatically with no re-check, so the allowlist applies only to the first hop. A redirect from an allowlisted host — or any on-path attacker, since the Wayback CDX call is plain `http://` — can (a) make Zone A send packets to the engagement target, breaking the "RECON_PASSIVE sends zero packets to the target" invariant, and (b) inject fake "archived URLs" into the graph, steering HYPOTHESIZE toward attacker-chosen assets. No read-size cap either.
- **When it breaks:** any passive-recon run where web.archive.org is MITM'd (realistic on client LANs / untrusted Wi-Fi during pentests) or an allowlisted host redirects off-list.
- **Fix:** custom `HTTPRedirectHandler` that raises `ZoneAViolation` on any redirect (or disables redirects and re-issues manually), switch the CDX URL to `https://`, cap `r.read()`.

### H4. Sandbox image is not pinned by digest — mutable `:latest` is the default

- **File:** `src/kryonsec/config.py:180-184`, consumed at `sandbox.py:58` / `runner.py:143`
- **What's wrong:** CLAUDE.md rule 7 says "sandbox image is pinned by digest". The code defaults to `kryonsec/sandbox:latest`; `_image_present` accepts any tag; `KaliSandbox._docker_argv` runs whatever string is configured with no `@sha256:` check. Anyone who retags `:latest` silently changes the code that runs with network access to the target. `sandbox.py`'s own docstring says "pinned image", contradicting the code. `install.sh` also builds/tags `:latest`.
- **Fix:** default to a digest, and refuse non-digest references in `sandbox_available`/`KaliSandbox.__init__`.

### H5. Zone B egress is default-bridge — "target-scope only" is not enforced at all

- **File:** `src/kryonsec/purple/sandbox.py:80-84` (self-acknowledged in a comment; also `exploit.py:218-221`)
- **What's wrong:** the spec's traffic-shaping proxy (§8.2) does not exist; containers use the default bridge, which reaches the host's network and the internet. The only scope control on what sandboxed tools touch is argv construction — which H2 shows is bypassable. Combined, tools inside the "sandbox" can connect to arbitrary hosts.
- **Fix:** ship the egress proxy (or interim: docker network with an egress allowlist of the target's resolved IPs) before enabling Zone B; until then keep the halt instead of running default-bridge.

### H6. The agent's `cve_lookup` tool always fails — `cfg` is never passed

- **File:** `src/kryonsec/copilot/agent.py:140-142` vs `cve.py:110` (`def lookup_cve(cfg, cve_id)`)
- **Verified:** reproduced — `execute_tool(tb, "cve_lookup", '{"cve_id": "CVE-2024-1234"}')` → `error: bad arguments for cve_lookup: lookup_cve() missing 1 required positional argument: 'cfg'`.
- **What's wrong:** `toolbox["cve_lookup"] = (TOOL_SCHEMAS["cve_lookup"], bounded(lookup_cve))` — the executor is invoked as `executor(cve_id=...)` without `cfg`. Every LLM call to it fails. `web_search` right above does it correctly (`lambda query: search_web(cfg, query)`).
- **Fix:** `bounded(lambda cve_id: lookup_cve(cfg, cve_id))`.
- **Test masking:** `test_agent.py:104-107` asserts only *presence* of the tool, never executes it.

### H7. MCP tool schemas advertise the raw name but the toolbox key is prefixed — every MCP call is rejected as "unknown tool"

- **File:** `src/kryonsec/copilot/mcp_tools.py:43` (`toolbox[f"mcp_{name}"]`) vs `:130` (`"name": getattr(tool, "name", "tool")`)
- **Verified:** both lines confirmed in code.
- **What's wrong:** `run_agent` advertises the schema names (e.g. `echo`) to the LLM; `execute_tool` dispatches on toolbox keys (`mcp_echo`) → `"error: unknown tool 'echo'"`. MCP tools can never be invoked by design. Same-named tools from different servers also silently collide.
- **Fix:** rewrite the schema name when registering: `schema["function"]["name"] = f"mcp_{name}"`.
- **Test masking:** `test_agent.py:110-115` injects a fake whose schema name already equals the key — the mismatch is never exercised.

### H8. MCP tool executors run the session coroutine on the wrong event loop

- **File:** `src/kryonsec/copilot/mcp_tools.py:140-151`
- **Code:**
  ```python
  def call(**kwargs):
      result = anyio.run(session.call_tool, tool_name, kwargs)
  ```
- **What's wrong:** the `ClientSession` and streams are created inside `anyio.run(self._run_bg, ...)` on a daemon thread parked in `sleep_forever()`. The executor later calls `anyio.run(...)` on the **main thread** — a second, unrelated event loop. Awaiting futures bound to the background loop raises `RuntimeError` ("Future attached to a different loop") or deadlocks with no timeout. Even after fixing H7, the first real MCP call would fail or hang.
- **Fix:** keep one loop on the background thread (`loop.run_forever()`) and marshal calls with `asyncio.run_coroutine_threadsafe(...).result(timeout=...)`.

### H9. MCP servers are re-spawned on every chat turn and never torn down

- **File:** `src/kryonsec/cli.py:296-301` (inside the `while True` chat loop), with `mcp_tools.py:91-104, 153-155`
- **What's wrong:** every user message runs `_build_mcp_extra(cfg)` → a fresh subprocess + daemon thread per configured server; the previous turn's toolbox is dropped and nothing terminates it (`close()` clears `self.sessions`, which is never populated anywhere — a no-op). After 50 chat messages you have 50 copies of each MCP server running until the CLI exits, plus up to 5 s latency per message while servers boot.
- **Fix:** build the MCP toolbox once before the loop; make `close()` actually cancel loops / terminate processes.

### H10. `shlex.split` mangles Windows paths — MCP servers can never start on Windows

- **File:** `src/kryonsec/copilot/mcp_tools.py:54-55`
- **Verified:** reproduced end-to-end by the audit agent against a working stdio MCP server — `shlex.split(r"C:\Users\...\python.exe")` strips every backslash → `[WinError 2]` after the 5 s timeout.
- **What's wrong:** POSIX-mode `shlex.split` treats `\` as an escape. Any `[mcp] servers` command given as a Windows absolute path fails to spawn (surfacing only as a log warning). Additionally `npx`-based presets can't spawn at all on Windows (`npx` is `npx.cmd`; CreateProcess won't execute `.cmd` without a shell).
- **Fix:** `shlex.split(command, posix=False)` on Windows + strip quotes — or better, store `command`/`args` as an explicit argv list in config (matches the project's own argv-lists rule).

### H11. `install.ps1` cannot run under Windows PowerShell 5.1 — the interpreter its own one-liner invokes

- **File:** `install.ps1:31`
- **Code:**
  ```powershell
  Die "Python 3.11+ required (found: $($version ?? 'unknown')). ..."
  ```
- **Verified on this machine:** `powershell -Command "$v = $null; $v ?? 'x'"` → `Unexpected token '??'`.
- **What's wrong:** `??` requires PowerShell 7; stock Windows 11 ships 5.1 as `powershell`. PowerShell parses the whole script before executing, so the entire script fails to parse — the advertised `powershell -c "irm ... | iex"` one-liner dies before installing anything.
- **Fix:** `$(if ($version) { $version } else { 'unknown' })`, or document `pwsh -c ...`.

## MEDIUM

### M1. HYPOTHESIZE sends engagement data (incl. query strings with tokens) to a third-party LLM unredacted

- **File:** `src/kryonsec/purple/hypothesize.py:112-131`; data from `zonea.py:231-235`
- **What's wrong:** `propose_hypotheses` calls `cfg.general_search_model` (default `gpt-4o-mini`) with subdomain lists and Wayback paths **including full query strings** — which routinely contain session tokens, reset links, API keys. No redaction, no secret detection; the only routing is "fall back to local if no OpenAI key" (which also misses `openai/gpt-4o`-style litellm strings). Violates rule 4 ("engagement data … never sent to third-party LLMs").
- **Fix:** route purple-team LLM states through the same redaction / local-routing gate as compaction (spec §6.4), or force `cfg.local_model`; strip query-string values from paths before templating.

### M2. REPORT crashes with `UndefinedError` when HUMAN_REVIEW failed — report.md is never written

- **File:** `src/kryonsec/templates/report.jinja:11`, path via `report.py:77-83` and `human_review.py:105`
- **Verified:** reproduced empirically — `REPORT CRASHED: UndefinedError 'dict object' has no attribute 'approved'`.
- **What's wrong:** `selectattr('approved', 'equalto', true)` on a StrictUndefined env raises for hypotheses missing the `approved` key — which is exactly the state when the human reviewer crashed (`human_review.py:91-96` returns early without setting it). `ReportSubagent.run` is the only subagent with no try/except, so the exception escapes and no report file is produced — precisely in the scenario where the operator most needs a record.
- **Fix:** build hypothesis dicts with `"approved": n["properties"].get("approved", False)` (the template already uses `| default(false)` elsewhere) and wrap the render in try/except that audits `report_failed`.

### M3. The report's "final fingerprint" never matches the audit chain's real head — and hides tail truncation

- **File:** `src/kryonsec/purple/report.py:94` vs `:165-169`
- **Verified empirically:** printed anchor `dab137a…` vs real head `802825f…`.
- **What's wrong:** `audit_head=audit.head_hash()` is captured at render time, then `report_written` (and possibly `report_validation_failed`) entries are appended **after** it. Consequences: (a) a verifier following the report's own instruction gets a mismatch on every untampered engagement; (b) deleting only the final audit line makes the chain head equal the printed anchor — that truncation is invisible to the anchoring scheme.
- **Fix:** append the `report_written` entry before rendering the anchor (or patch the anchor line after the final append).

### M4. The budget HALT is dead code — nothing ever updates `BudgetTracker`

- **File:** `src/kryonsec/purple/orchestrator.py:34-47`, checked at `:100-103`
- **Verified:** grep — `used_tokens` / `used_cost_usd` / `elapsed_s` appear only in the class definition; no writer anywhere.
- **What's wrong:** `run()` checks `budget.exhausted()` every iteration, but it can only ever be False (unless constructed pre-exhausted). A real engagement can burn unbounded tokens, cost, and wall-clock time; the spec's §4.3 budget guard is decorative. `test_budget_exhaustion_halts` masks this by constructing `BudgetTracker(max_tokens=0)`.
- **Fix:** at minimum `budget.elapsed_s = time.monotonic() - start` each iteration; accrue tokens/cost at the LLM call sites.

### M5. VERIFY marks findings "verified" on any page difference — false confirmations on dynamic content

- **File:** `src/kryonsec/purple/verify.py:157` — `responses_differ = true_out != false_out`
- **What's wrong:** the true/false probes are two separate HTTP fetches compared by raw byte equality. Any page with a timestamp, CSRF token, session id, or rotating content differs between *both* a vulnerable and a non-vulnerable parameter → `verified: True`, an audit `finding_verified` event, and "Double-checked: yes" printed in the report for a finding never actually confirmed. The classic boolean technique compares both responses to a **baseline** fetch.
- **Fix:** fetch a baseline (unmodified param), require `true ≈ baseline and false ≠ baseline` with normalization, or compare lengths (`true_len`/`false_len` already recorded) with a threshold.

### M6. VERIFY probes the wrong host for subdomain-targeted findings

- **File:** `src/kryonsec/purple/verify.py:122`
- **Verified:** reproduced — exploit probes `http://webmail.t.com/showthread.asp?id=1`, verify probes `http://t.com/webmail.t.com/showthread.asp?id=1`.
- **What's wrong:** EXPLOIT passes `self._subdomains` to `compose_url` so `/webmail.t.com/x` routes to the subdomain host; VERIFY passes no subdomains, so the same asset resolves to a path on the **main host**. The "independent confirmation" runs against a different server than the one that produced the finding — can falsely verify or falsely fail. `VerifySubagent` never collects `graph.by_type("subdomain")` at all.
- **Fix:** `subs = [n["label"] for n in self.graph.by_type("subdomain")]; compose_url(self.target, asset, subs, ...)`.

### M7. Seccomp profile is silently skipped in every real installation

- **File:** `src/kryonsec/purple/sandbox.py:43-44, 61-63, 78-79`
- **What's wrong:** `_repo_root()` is `Path(__file__).resolve().parents[3]` — the repo root only for a source checkout. In the installed venv (`site-packages/kryonsec/purple/sandbox.py`), `parents[3]` is the lib dir; the profile is never there, and `is_file()` makes the omission silent. The docstring and spec §8.5 claim seccomp is applied. Tests codify the skip (`test_sandbox.py:20-22`).
- **Fix:** ship the profile as package data and resolve via `importlib.resources`, or refuse to spawn when configured-but-missing.

### M8. `run_agent` bypasses `chat()`'s provider guards — unpulled Ollama model hangs 60 s per turn

- **File:** `src/kryonsec/copilot/agent.py:209-217`
- **What's wrong:** `chat()` calls `_ollama_model_ok` (llm.py:126-140) before litellm because Ollama silently hangs for unpulled models; `run_agent` calls `litellm.completion` directly and gets none of that precheck or the within-provider fallback. With `provider == "ollama"` and an unpulled model, every turn blocks the full 60 s timeout before erroring.
- **Fix:** route the per-round call through `chat()` or call `_ollama_model_ok` once at the top of `run_agent`.

### M9. `_run_purple` checks the wrong sandbox image

- **File:** `src/kryonsec/cli.py:411` — `sandbox_available()` without `cfg.sandbox_image`, vs `tui.py:35` which passes it
- **What's wrong:** the CLI preflight probes the default `:latest` while the TUI toggle validates the configured (possibly digest-pinned) image — two code paths disagree about the same prerequisite. With `KRYONSEC_SANDBOX_IMAGE` set to a pulled digest while `:latest` isn't, purple mode passes the toggle then halts with a wrong "Sandbox not available".
- **Fix:** pass `cfg.sandbox_image` at `cli.py:411`.

### M10. `openai_key` pattern misses modern `sk-proj-…` keys

- **File:** `src/kryonsec/secrets.py:31-33` — `r"\bsk-[A-Za-z0-9]{20,}\b"` (verified)
- **What's wrong:** standard OpenAI keys since 2024 are `sk-proj-…` / `sk-svcacct-…` — the char class excludes hyphens, so 4 chars after `sk-` hits `-` and the match fails. The key is not detected, compaction treats the text as secret-free, and (per C2) the raw key ships to the provider — the exact failure the redaction layer exists to prevent.
- **Fix:** `r"\bsk-(?:proj-|svcacct-)?[A-Za-z0-9_-]{20,}\b"`.

### M11. Unguarded exceptions crash the whole CLI and lose the session

- **Files:** `src/kryonsec/cli.py:288` (`await session.maybe_compact()` — no try/except) and `:330-345` (fallback `chat()` catches only `LlmUnavailable`)
- **What's wrong:** (a) `maybe_compact` can raise `CompactionMustStayLocal` (secrets present + Ollama down) or a raw Ollama/litellm error — both propagate out of `_chat_loop` past `main()`'s `except KeyboardInterrupt` and dump a traceback; the session is only persisted on `/quit`, so all context is lost. (b) In the agent fallback, `chat()` on the ollama path raises non-`LlmUnavailable` exceptions (timeout, connection reset, wrong-tag model from M12) that are uncaught — the fallback is strictly less protected than the primary path it rescues.
- **Fix:** wrap both in the same broad `except Exception` as the primary path; for compaction, degrade to "skip compaction" with a warning.

### M12. Wizard strips non-`latest` Ollama tags, producing a model id that doesn't exist

- **File:** `src/kryonsec/wizard.py:272` — `base = model.split(":")[0]`
- **What's wrong:** only `:latest` is safe to strip. `llama3.1:8b` → `ollama/llama3.1`; the preflight in `_ollama_model_ok` matches on the base name so it *passes*, but Ollama resolves a bare name to `:latest`, which isn't pulled → runtime failure (which then escapes via M11).
- **Fix:** strip only a literal `:latest` suffix. **Test masking:** `test_wizard.py:177` asserts tag-stripping using only `:latest` models, locking the bug in.

### M13. Selecting zero tools in the wizard silently re-enables all tools on next launch

- **File:** `src/kryonsec/config.py:241-242` — `if tools.get("enabled"):`
- **Verified empirically:** round-tripping `enabled_tools = []` yields `['file_read', 'file_write', 'web_search', 'cve_lookup']`.
- **What's wrong:** the wizard writes `enabled = []` when the user deselects everything; on load the empty list is falsy so the branch is skipped and the dataclass default — all four tools **including `file_write`** — comes back. A user who explicitly disabled all tools gets file read/write re-enabled.
- **Fix:** `if "enabled" in tools:`.

### M14. `install.sh`: unguarded `git clone` aborts the installer before the wizard runs

- **File:** `install.sh:69`
- **What's wrong:** the `docker build` failure is tolerated (`|| say WARNING`), but the `git clone` one line above is not. Docker installed does not imply git installed. With `set -euo pipefail`, a missing git or network hiccup exits the script after the venv step but before `kryonsec setup` — half-configured install, no wizard.
- **Fix:** `git clone ... || { say "WARNING: could not fetch sandbox sources"; }` and guard the build on the clone succeeding.

### M15. No `migrations/` directory; `create_all`-only schema; purple DB models are dead code

- **File:** `src/kryonsec/storage/db.py:52-59`; `migrations/` does not exist anywhere in the repo
- **What's wrong:** rule: "schema changes go through migrations, never ad-hoc DDL" — unimplemented. `create_all` never alters existing tables, so the first schema-evolving release silently keeps old columns (or breaks) on existing databases. Additionally `PURPLE_TABLES` (`StmNode`, `Checkpoint`, `LtmTargetProfile`, `LtmEngagementSummary`, `EngagementSecretMap`) are referenced by zero purple modules (grep-verified) — engagement state lives only in memory + JSONL, so "PostgreSQL is the system of record" (spec §10.1) is not implemented for Mode B.
- **Fix:** add migrations matching the models; either wire purple state to the repository layer or remove the dead models.

### M16. Engine bootstrap logs the full `DATABASE_URL` — including the password

- **File:** `src/kryonsec/storage/db.py:48` — `log.info("storage backend: %s (%s)", cfg.storage_kind, url)`
- **What's wrong:** `postgres://user:password@host/db` goes verbatim to the log if the level is raised to INFO (default is WARNING, but any user/integration logging config exposes it).
- **Fix:** `sqlalchemy.engine.url.make_url(url).render_as_string(hide_password=True)`.

### L1. Mojeek snippet/result misalignment when nav links are skipped
- **File:** `src/kryonsec/copilot/websearch.py:206-215`
- Skipped `mojeek.com` links don't advance the snippet index (`snippets[len(results)]`), so every following result pairs with the wrong snippet. The test's own fixture demonstrates it and only asserts URLs. **Fix:** pair by position in `links`, not kept-result count. (`_from_ddg_lite` has the same class of issue with dedup.)

### L3. `except TypeError` mislabels internal tool bugs as "bad arguments"
- **File:** `src/kryonsec/copilot/agent.py:174-175`
- A `TypeError` raised *inside* a tool body is reported to the LLM as a signature problem (H6's symptom was laundered through exactly this branch). **Fix:** validate kwargs against the schema instead of catching `TypeError`.

### L4. Docstring/code contradictions
